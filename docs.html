treedb 元数据引擎

面向「大量小对象 + 高频点查 + 目录遍历 + 万级常驻连接」这一负载形状的元数据引擎： 单进程 epoll 事件循环、自定义二进制线协议、内存状态机 + CRC32 WAL + 快照 checkpoint。 POSIX 元数据语义，客户端无关。

单二进制 · 一个目录 52 个 op 协议版本 6 默认依赖仅 libc + thiserror

01概览

一句话

treedb 不是关系库，而是「把文件系统元数据的访问路径做成数据库」： 它只认 Lookup / ReadDir / Create / RowGet 这类点查与遍历， 用一次跨连接合并的 fsync 换掉「每写一次刷一次盘」，用每连接一个 fd 换掉「每连接一个后端进程」。

解决什么问题：负载形状

这四件事同时出现时，通用关系库会同时输在进程模型和写路径上：

负载特征关系库的代价treedb 的做法
大量小对象（元数据条目，几十到几百字节）行存 + 解析执行 + 事务框架，单条开销远大于有效载荷二进制 op 直接落在内存状态机上，无解析、无 SQL
高频点查（按路径查 inode）每条语句要过 planner / executorLookup 一次哈希 + 一次树查，单连接 9.5–10.1× PG（§7.11）
目录遍历（readdir 拉整目录属性）N 行结果集 + 每行的类型转换ReadDirPlus 一次回整目录 dentry + attr，单连接 11.4–11.9×（§7.11）
万级常驻连接（每个挂载点/客户端几条长连接）每连接一个 backend 进程，实测 ≈14 MiB，万级连接是百 GiB 量级每连接 1 个 fd、0.56 KiB RSS；25 000 条实测 fd/conn = 1.0000（§7.6）

核心架构

层实现关键位置
前端单进程 epoll；--workers N 时 N 条线程各自 accept（SO_REUSEPORT）、各自收发；只读 op 就地并行算src/net/multi.rs、src/net/server.rs
线协议自定义二进制帧，PROTOCOL_VERSION = 6；52 个 op，两个布尔判据切成 22 只读 / 23 真写 / 7 控制面三档src/engine/model.rs、src/net/codec.rs

副本pull 式日志传送：主只答 WalFetch/SnapFetch，不维护副本状态；副本是完整 Engine，只是真写被 EROFS 挡掉src/bin/standby.rs、src/net/replication.rs

与 PostgreSQL / SQLite 的定位差异

维度treedbPostgreSQLSQLite
进程模型单进程多 worker，共享一份内存状态每连接 fork 一个 backend进程内库（无网络层）
万级连接成本0.56 KiB/conn，1 fd/conn≈14 MiB/backend不适用（无服务端）
写持久化默认 group：跨连接合并成一次 fsync（实测 58.9–61.5 writes/sync）synchronous_commit=on：每事务一次synchronous=FULL：每条写一次，无组提交
查询表达力无 SQL、无 JOIN、无范围/排序/聚合完整 SQL完整 SQL
事务单 op 原子；无跨 op 事务、无跨视图原子多语句事务 + MVCC多语句事务
部署一个二进制 + 一个目录initdb + 服务 + 配置 + 连接池一个文件（嵌入式）
适用形状元数据点查 + 目录遍历 + 海量长连接通用 OLTP / 分析单机嵌入式
这是定位差异，不是功能残缺

用 treedb 存业务数据、做报表、跑 JOIN，是选错了工具。它的表达力上限就是 「按主键读 / 按已建索引列等值列举 / 键游标翻页 / 计数」，这条边界写在 §5.3 与 §4.2， 没有隐藏的全表扫兜底——查未建索引的列直接 EINVAL。

02安装与构建

一句话

默认档 cargo build --release 只拉 libc 与 thiserror 两个依赖， 产出 7 个命令；treedb-demo / treedb-pgbench / treedb-sqlitebench 不在默认档里，必须开 --features postgres-compat。

依赖要求

项要求说明
Rust 工具链稳定版，支持 edition 2021仓库没有 rust-version 下限声明，也没有 rust-toolchain.toml；用当前 stable 即可
运行时依赖仅 libc + thiserror无 C 库、无 OpenSSL、无 protobuf、无异步运行时（不用 tokio）
可选依赖（7 个）只在 postgres-compat 下进入构建图postgres / rusqlite(bundled) / parking_lot / uuid / sha2 / chrono / tracing
构建时 C 编译器默认档不需要开 postgres-compat 时 rusqlite 用 bundled，需要 cc
磁盘数据目录所在盘要支持 fsync 与稀疏文件WAL 预分配会形成空洞，--stats 把逻辑长度与磁盘长度分开报

编译步骤

# 2. 默认档：纯引擎，依赖只有 libc + thiserror

# 3. 跑测试（默认档 159 passed，引擎本体）

# 4. 可选：开过渡档（PG 共享池 + SQLite 镜像），190 passed
cargo build --release --features postgres-compat
cargo test  --release --features postgres-compat

# 5. 起一个实例
./target/release/treedb-server --dir /var/lib/treedb --listen 127.0.0.1:7777

feature默认内容何时开

旧数据目录要先 upgrade

从 SNAP_VERSION 2 的旧布局上来的目录，新二进制会拒收。这不是 bug，是 「不静默按错布局解字节」的故意选择。出路随包安装：

快照布局升级treedb-migrate
# 只报告，不写；退出码 10 = 需要迁移但没给 --apply
./target/release/treedb-migrate --dir /var/lib/treedb

# 执行迁移（只重写 state.snap，WAL 不动）；先停服务端
./target/release/treedb-migrate --dir /var/lib/treedb --apply

# 覆盖既有备份文件
./target/release/treedb-migrate --dir /var/lib/treedb --apply --force

退出码：0 = 无需迁移或已完成；1 = 出错（含拒动）；10 = 需要迁移但没给 --apply。 回滚是把自动落下的 state.snap.v2.bak 拷回去再跑旧二进制，但无损窗口只维持到新二进制做过第一次 checkpoint 之前。

03启动与连接

一句话

一个二进制 + 一个目录就能起：treedb-server --dir PATH --listen HOST:PORT； 11 个 flag 全部可选，默认值即生产默认（group / workers=auto / backlog=4096 / auto-checkpoint=64 MiB）。

服务端启动与参数详解

最小启动默认 127.0.0.1:7777 / group / workers=auto
# 目录不存在会自动创建
./target/release/treedb-server --dir /var/lib/treedb --listen 0.0.0.0:7777

# 生产常配：显式 worker 数 + 心跳间隔 + 自动 checkpoint 阈值 + pid 文件
./target/release/treedb-server \
  --dir /var/lib/treedb \
  --listen 0.0.0.0:7777 \
  --durability group \
  --workers 8 \
  --auto-checkpoint-mb 256 \
  --pid-file /run/treedb.pid

# 开接入认证（所有客户端、--stats、--shutdown 都得带同一把密钥）
./target/release/treedb-server --dir /var/lib/treedb --auth-key-file /etc/treedb/cluster.key
参数默认值含义与注意事项
--dir PATH/var/lib/treedb数据目录：WAL + 快照 + .lock + 可选 fence。目录级 flock 独占，第二个进程打不开同一个目录
--listen HOST:PORT127.0.0.1:7777监听地址。--workers > 1 时每条 worker 线程各自 bind（SO_REUSEPORT），同一端口由内核分发
--durability NAMEgroupgroup / always / never。拼错不是静默降级，而是退出码 2（见下节）
--workers N0 = autoauto = min(8, 核数/2)，至少 1。=1 是单线程事件循环，也是全部历史基线数字的档。>1 时每条 worker 多占 3 个 fd（1 监听 + 2 eventfd），且只扩展读
--backlog N4096listen(2) 的接受队列长度，受 net.core.somaxconn 截断。建连风暴时真正起作用的是它和客户端源端口数
--sync-ms N20事件循环空闲唤醒间隔。0 与「不给」是两件事：前者关掉周期 sync
--auto-checkpoint-mb N64WAL 逻辑长度超此值自动 checkpoint；0 = 关闭。别在生产关掉，否则 WAL 只增不减
--max-conn N0 = 不限同时在册连接数上限。超额的连接accept 后立刻关闭（客户端看到 EOF，不发任何帧）；日志限速（第 1 条 + 之后每 1000 条），总数在停服汇总的 accepted / refused / peak 里
--pid-file PATH不写启动后写入 pid，便于脚本 kill -9 做崩溃验收
--auth-key-file PATH不认证集群共享密钥：32 原始字节或 64 个十六进制字符；全零（0/64 个 0）视为未填模板，拒接
--stats—不启服务：连上去打印状态后退出。用 --listen 指目标，不需要 --dir
--format text|prometheustext只对 --stats 生效。prometheus 输出 27 个指标（每条严格 HELP/TYPE/样本三行）；拓不到服务时仍输出 treedb_up 0 并以退出码 1 退出（面板上是 down，不是 no data）
--shutdown—不启服务：通知运行中的实例优雅停服（补 fsync + checkpoint）
退出码约定

2 = 参数错误（usage error，如 --workers abc）；1 = 运行期 FATAL （如 WAL fsync 失败）。后者绝不能当正常退出——此时内存状态可能已超前于磁盘。 SIGINT/SIGTERM 走优雅退出路径，不是直接 kill。

durability 三档：换的是什么

档位落盘语义断电会丢什么实测
group（默认）每轮把所有连接 staged 的写打成一个批，只做一次 fsync，然后整批应答已 ack 的写在同一次 fsync 里，正常断电不丢每次 fsync 摊 58.86 条写（机械盘）/ 61.48 条（ext4）
always与 group 同一个落盘点：已 ack 的写必已落盘。不再按连接串 fsync不丢已 ack 的写syncs/writes = 1.00；同负载 QPS 1 469，group 为 10 913（7.4×）
never不调 fsync，靠内核回写断电丢最近若干条已 ack 的写；但 WAL 有 CRC32，不会解出错数据只用于测试与可重放负载
为什么 always 不再是「一条连接一个 fsync」

旧实现里 always 按连接串行刷盘，64 并发写时 p99 到 315 ms。现在 always 与 group 共用同一个落盘点，区别只在「是否等这一轮 fsync 返回才 ack」。 换盘/换文件系统时 always 的差距可达 8×，这是介质属性，不是引擎参数能消掉的。

客户端连接

线协议是 TCP 上的自定义二进制帧，地址格式就是 host:port。Rust 客户端在 treedb::net::client::Client，两个构造函数：

客户端两种建连方式Rust
use treedb::engine::{Op, Reply};
use treedb::net::client::Client;
use treedb::net::auth::Key;

// 1) 不认证（服务端没给 --auth-key-file）
let mut c = Client::connect("127.0.0.1:7777", 3000)?;   // 第二参数是读超时 ms，0 = 不设

// 2) 带认证：握手不通过就返回 Err，绝不静默降级成不认证
let key = Key::load("/etc/treedb/cluster.key")?;
let mut c = Client::connect_auth("127.0.0.1:7777", 3000, Some(&key))?;
完整调用：建视图 → mkdir → 查属性Rust
let v = match c.call(&Op::CreateView { name: b"demo".to_vec() })? {

c.call(&Op::Mkdir {
    view: v, parent: 1, name: b"etc".to_vec(),
    mode: 0o755, uid: 0, gid: 0,

let ino = match c.call(&Op::Lookup { view: v, parent: 1, name: b"etc".to_vec() })? {
    Reply::Node(n) => n.ino,
    Reply::Err { code, .. } => panic!("lookup 失败 errno={code}"),
    other => panic!("{other:?}"),

认证握手（CHAP 双向挑战，默认关）

四帧、两个方向各解一次挑战。两方向的 ctx 串不同、nonce 顺序相反，所以把一方的 应答原样回放给另一方不成立；server_nonce 每轮新取，重放直接失效。

帧op携带校验
1AuthBegin 0x0090客户端 nonce a—
2AuthChallenge 0x0190服务端 nonce b + 服务端 MACMAC = HMAC(key, ctx_b‖VER‖b‖a)
3AuthFinish 0x0091客户端 MACMAC = HMAC(key, ctx_a‖VER‖a‖b)
4AuthOk 0x0191label / ro / view / owner之后才允许发数据 op
生成密钥文件两种合法格式
# 32 原始字节
head -c 32 /dev/urandom > /etc/treedb/cluster.key
chmod 600 /etc/treedb/cluster.key

# 或 64 个十六进制字符
head -c 32 /dev/urandom | xxd -p > /etc/treedb/cluster.key

# 全零模板会被拒：Key::load 对 0 字节 / 64 个 '0' 直接报错
开了认证之后，--stats 与 --shutdown 也要带密钥

否则它们拿到的不是「无权限」，而是握手阶段就被断开。脚本里三处要一起改： 服务端、运维命令、客户端。密钥必须与副本的 --auth-key-file 是同一把， 否则表现是 lag 永远追不上（副本指数退避重试），而不是一个明确的错。

认证只管「你是谁」，不管「你能干什么」

一把密钥开整扇门：握手通过后 52 个 op 全部可用，包括 Shutdown 与 Checkpoint。不做授权、不做审计级隔离、不加密传输（明文 TCP）、不防字典攻击、 也不能证明对端是「当前主」而不是一个旧主。这四条写在 DESIGN §4.4 末尾与 §8 第 13 条。

04使用指南

一句话

两套 API 共用一条连接：POSIX 元数据 op（视图 + 目录树 + 属性 + 链接 + 引用账本 + 锁） 和通用表 op（9 条，等值 + 键游标，无 SQL）。运维只多三条：Stats、Checkpoint、Shutdown。

POSIX 元数据 API

全部 op 以 ViewId 隔离命名空间：同一个引擎里可以有上万个视图， 每个视图有独立的根 inode（root = 1）。视图隔离是命名空间隔离，不是访问控制。

锁是「整 inode + 租约」，不是 POSIX 记录锁

引擎没有 (pid, fd) 概念，所以给不了字节区间仲裁。grovefs 适配层因此把 lock_op 做成无条件 EPERM 桩、get_lock 回 None—— 「给错语义比给不了更糟」。

pipeline 批量请求

一条连接上连发 N 个请求、再一次性收 N 个回包，保序。这是吞吐轴上的主要杠杆： 它把「一次往返」和「一轮 fsync」都摊到 N 个 op 上。

规则说明
保序同连接内按发送序回填，应答身份用从不复用的连接号，不是 fd（fd 会被内核复用）
只读就地算workers > 1 时，整批全是只读 op 才由 worker 就地执行
含写整批转发一个批次里只要有一条写，整批交给提交线程；该连接上还有未回话的转发 op 时，后续批次也一律转发
p50/p99 口径按「批次总耗时 / N」计，即每 op 摊销延迟；报批次延迟会让 pipeline=32 看起来像 1 ms 级

WAL 膨胀与自动 checkpoint 策略

项行为注意
触发条件WAL 逻辑长度 > --auto-checkpoint-mb（默认 64 MiB）看的是逻辑长度，不是磁盘占用
关闭方式--auto-checkpoint-mb 0WAL 只增不减，磁盘会被预分配吃光，只在测试里用
同步 checkpoint显式 Op::Checkpoint / 优雅停服；写完快照后 wal.reset()会物理抹掉水位以下的 WAL 文件内容
自动 checkpoint写完快照后 truncate_before不开归档时同样不保留历史分段，因此没有 PITR；带 --archive-dir 起步则先把段与旧快照拷进归档再抹，PITR 可用（§6.11）
快照自校验尾巴 16 字节 = crc32 + seq + magic水位对不上就拒收，不静默按错布局解字节
启动恢复读快照，再把 snap_seq 之后的 WAL 重放完重放条数与耗时在停服日志里报一行（recovered N wal recs）

数据目录互斥：.lock

目录里有一个 .lock 文件，Engine::open 用 flock(LOCK_EX|LOCK_NB) 拿独占， 再叠一层进程内注册表（同进程再 open 同一个目录也拒，因为 flock 对同进程会放行）。 这一层是所有离线工具的前提：

命令要求被占时的表现
treedb-server独占 --dir启动失败，报目录被占
treedb-dump独占源目录拒绝导出——宁可拒也不猜「快照 + 正在增长的 WAL」
treedb-load目标目录为空或不存在退出码 1
treedb-migrate不做互斥，须人工先停服可能在服务运行中改快照，务必先停
treedb-standby --promote独占副本目录须先停 standby 进程
目录锁挡不住「第二个进程绑同一端口」

SO_REUSEPORT 允许另一个进程并列 bind 同一个端口。如果它指向另一个目录， 两个实例会同时对外服务——单实例靠部署约束，不是靠内核。指向同一目录则被 .lock 挡住。

fence 文件与 fencing token

<dir>/fence 是一个十进制整数文件。它随每条 WalBatch 与 SnapChunk 的尾部 epoch 一起传播，Engine::admit_epoch 据此做三档判定：接受、拒收、要求重同步。

看令牌 / 抬令牌直接 cat 就能看见
# 当前值（没有这个文件 = 0）
cat /var/lib/treedb/fence

# 抬一级：离线动作，抬完就退出（不起服务）
./target/release/treedb-standby --dir /var/lib/treedb-replica --promote
# promoted /var/lib/treedb-replica: fence 0 -> 1 (snap_seq 40024, 40024 wal recs replayed)
三条禁令

① 别把新主的 fence 改小——那等于把旧主的权开回来。
② --promote 不能与 --primary 同给（自相矛盾，退出码 2）。
③ 提升不会让旧主停手：fence 只让副本拒收旧主的批，挡不住旧主继续服务它自己的客户端。 旧主必须真停，或者把客户端改指到新主。仍指着旧主的其他副本会拒收它的批（日志 is fenced out），需改指新主。

  --primary 10.0.0.11:7777 \
  --dir /var/lib/treedb-replica \
  --listen 0.0.0.0:7778 \
  --interval-ms 20 \
  --fetch-bytes 1048576

# 主：--auth-key-file /etc/treedb/cluster.key
# 副本：--auth-key-file /etc/treedb/cluster.key

副本参数默认说明
--primary HOST:PORT必填主的地址；副本单向拉，主不感知
--dir PATH/var/lib/treedb-replica必须与主目录分开：各自有 WAL 与快照，落盘字节可直接比对

--fetch-bytes N1048576一次往来的负载上限，受协议 WAL_FETCH_MAX 约束；追得慢就调大
--timeout-ms N5000到主的连接与读写超时；必须有上限，否则不答话的主会把读全钉死
--auto-checkpoint-mb N64副本 WAL 只能靠追平增长，别关
--workers N0 = auto只扩展读；写永远到不了提交线程
它能当什么用

主机/磁盘/机房故障时的 DR 源：副本自带 WAL + 快照，可以直接当主起服； 副本重启也不需要向主全量重拉（先 WAL 后 apply）。主崩后副本仍能答读。

它不能当什么用

不能防误删。异步复制会把删除也传过去，副本只有「当前一份」，没有历史版本。 「恢复到上周三 14:00」在不开归档时给不了——checkpoint 会抹掉水位以下的日志；带上 --archive-dir 起步，之后 treedb-pitr --to-seq 就能落在这个粒度上（§6.11）。

热副本负责 RPO≈0 的切换，离线 dump 负责「回到某个日期」。单靠热副本不算完整备份： 可以每夜停副本 → 从副本 treedb-dump 一份 → 重新起副本，主全程不停；v0.6.0 起更省事的是主不停、副本也不停，直接 treedb-backup --primary … --out - | gzip 拿一份一致切面（§6.10）。

07恢复

一句话

四条路各对应一种故障：目录还在 → 直接起服；有 dump → treedb-load 到空目录； 主机没了 → 副本 --promote 后起服；进程崩了 → 什么都不用做，重启即重放。

从冷备份 / dump 恢复

路径 1：目录级恢复RPO = 备份时刻
# 1) 确认目标机上没有实例占用这个目录
# 2) 拷回去（保持 -a：权限/时间/稀疏）
cp -a /backup/treedb-2026-11-21 /var/lib/treedb

# 3) 起服
./target/release/treedb-server --dir /var/lib/treedb --listen 0.0.0.0:7777

# 4) 对拍四项
./target/release/treedb-server --listen 127.0.0.1:7777 --stats \
  | grep -E '^(nodes|dentries|refs|seq) '
路径 2：dump 恢复跨版本 / 跨机器
# 先体检：只解码 + 打规模，不写盘（退出码 0 = 通过）
./target/release/treedb-load --in /backup/treedb.dump

# 再落成新目录（目标须为空或不存在）
./target/release/treedb-load --in /backup/treedb.dump --dir /srv/treedb-new

# 从标准输入读（配合 gzip -dc）
gzip -dc /backup/treedb.dump.gz | ./target/release/treedb-load --in - --dir /srv/treedb-new

# 起服
./target/release/treedb-server --dir /srv/treedb-new --listen 0.0.0.0:7777
treedb-load 退出码含义
0导入完成，或（单参数模式）体检通过
1出错：CRC 不过 / 版本不认 / 目标非空或被占
2参数不全
load 只写快照，不写 WAL

水位 = dump 的 seq，所以新目录起来后 seq == snapshot、WAL 逻辑长度为 0。 dump 会带上未 durable 的记录（与启动恢复同语义）——那是磁盘上真实存在的写，丢掉才是错。

从副本提升为主

切主四步顺序不能乱
# 0) 前提：旧主必须真停（fence 挡不住它继续服务自己的客户端）

# 1) 停掉副本进程（它运行中是只读引擎，真写被 EROFS 挡）
#    kill -TERM <standby-pid>

# 2) 离线抬 fence：max(见过的) + 1，打印后退出，不起服务
./target/release/treedb-standby --dir /var/lib/treedb-replica --promote
# promoted /var/lib/treedb-replica: fence 0 -> 1 (snap_seq 40024, 40024 wal recs replayed)

# 3) 用同一个目录起新主
./target/release/treedb-server --dir /var/lib/treedb-replica --listen 0.0.0.0:7777

# 4) 验证 + 检查 fence 值
cat /var/lib/treedb-replica/fence
./target/release/treedb-server --listen 127.0.0.1:7777 --stats
检查项为什么
旧主是否真停fence 只让副本拒收旧主的批，旧主自己的读者不受影响
fence 是否 > 旧主的值否则旧主的批会被接受，两份数据分叉
是否误把 fence 改小等于把旧主的权开回来
其他副本是否仍指着旧主它们会拒收旧主的批（日志 is fenced out），必须改指新主
客户端是否改指新主--promote 不改任何客户端配置

崩溃恢复：重启即重放

进程被 kill -9、机器断电（group/always 档）后，重新起服即可： 引擎先读 state.snap，再把 snap_seq 之后的 WAL 全部重放完，然后才开始接受连接。

崩溃后重启停服日志会给一行重放报告
./target/release/treedb-server --dir /var/lib/treedb --listen 0.0.0.0:7777

# 停服时的报告（stderr）：
# shutdown: recovered 40024 wal recs (37 ms, snap 0) | accepted ... | ops ... | checkpoints ...
故障结果
kill -9 / 进程崩溃重启后已 ack 的写全在（有专门验收测试）
断电（group 档）已 ack 的写必已落盘；未 ack 的可能丢
断电（never 档）丢最近若干条已 ack 的写；WAL CRC32 保证不会解出错数据
快照损坏（CRC/水位对不上）拒收，不静默按错布局解字节——此时只能靠副本或备份
WAL 尾部半条记录CRC 不过的尾记录被丢弃，重放到最后一条完整记录

恢复后验证清单

nodes与备份时刻相等

09已知限制与 FAQ

一句话

它把「元数据点查 + 目录遍历 + 海量长连接」这一件事做深，其余一概不做： 没有 SQL、没有用户体系、没有加密传输、没有同步复制、没有自动故障转移。选型时先确认你不需要这些。

不做的事

类别明确不提供后果 / 替代
查询语言SQL、JOIN、排序、范围/前缀谓词、聚合、NULL/类型、外键/CHECK只有 9 条表 op：主键读、索引列等值列举、键游标分页、计数
事务多语句事务、跨视图原子单 op 原子；跨视图一致性由调用方负责
用户体系账号、角色、scope / ACL、租户、配额只有集群共享密钥（默认关）；握手通过后 52 个 op 全部可用
传输安全TLS、加密握手明文 TCP；需要就套 stunnel / WireGuard / 内网
复制同步复制、复制槽、级联副本、传输加密只有异步 pull 副本；跟不上就重装快照
高可用自动故障转移、被降级者自知--promote 是人工离线动作；租约/心跳与自动切换不在近期计划
备份冷拷、离线 dump/load、热副本、在线切面、WAL 归档、按 seq 的 PITR六形状见 06 章；增量与加密不做，要日切可以夜间 treedb-backup 一份

扩展属性xattr、ACL、quota无
规模声明状态全内存；最大规模未做实测节点数上限取决于内存，部署前按「每节点字节数 × 规模」估算并留余量

跨连接可见性先于持久性

这条语义容易误读

workers > 1 时，一条连接 ack 之后，其他连接立刻能看到这条写； 但「可见」不等于「已 fsync 到盘」。也就是说：一个客户端可能读到另一个客户端尚未落盘的写。 进程崩溃不会让已 ack 的写消失（会重放），但断电在 never 档可能丢尾部。

同连接内的顺序是严格的：一条批次里只要有写，整批交给提交线程；该连接上还有未回话的转发 op 时， 后续批次也一律转发——否则客户端会看到「我前一次写还没确认，后一次读已经看不到它」。

哪些能力由 grovefs 适配层维护

能力引擎侧适配层侧（grovefs）
POSIX 记录锁 / flock 区间仲裁只有整 inode 锁 + 租约（LockSet/LockQuery）lock_op 无条件 EPERM 桩、get_lock 回 None——「给错语义比给不了更糟」

连接管理只认 TCP 连接连接池：每进程 4 条（GROVEFS_TREEDB_CONNS），10 000 视图实测引擎侧 socket 恒 4
密钥 / 权限只做接入认证，一把钥匙开整扇门api_keys 表带 scope / view / ro / owner，权限在适配层判

FAQ

Q1. 能直接当 SQL 数据库用吗？

不能，也不打算。没有 SQL 解析器、没有 JOIN、没有排序与范围扫描。 需要这些就继续用 PG，treedb 只接元数据那一路。

Q2. 能多主同时写吗？

不能。单主假设：同一目录由 .lock 独占；副本对真写返回 EROFS。 SO_REUSEPORT 允许第二个进程绑同一端口，但同一个目录它打不开——单实例靠部署约束。

Q3. 主挂了能自动切到副本吗？

不能。切主是四步人工动作（停旧主 → 停副本 → --promote → 起服）。 租约/心跳与自动故障转移明确不在近期计划里（§11）。

Q4. 能存文件内容吗？

只存引用，不存字节。RefUp/RefDown/RefLookup 记的是 「哪个 data_ref 被几个持有者引用、共多少字节」，用于 GC 判据；内容本体在外部存储。

Q5. 视图之间有权限隔离吗？

没有。视图是命名空间隔离（dentry 键带 view id），不是访问控制。 任何通过握手的客户端可以操作任意视图。权限判断在 grovefs 的 api_keys 层。

Q6. 传输加密吗？

不加密。握手用的是 HMAC 挑战应答，防的是「没有密钥的连接」，不是防窃听。 跨公网请套隧道。

Q7. 单机能扛多少连接？

实测 25 000 常驻全绿（fd/conn = 1.0000、0.31 KiB/conn）。50 000 的失败是 客户端源端口耗尽（EADDRNOTAVAIL），服务端没有连接数上限常量。 真要更高，先扩 ip_local_port_range / 加客户端 IP。

Q8. 升级会丢数据吗？

treedb-migrate --apply 只重写 state.snap，不动 WAL，并自动落下 state.snap.v2.bak。无损回滚窗口维持到新二进制做过第一次 checkpoint 之前—— 之后同步 checkpoint 会 wal.reset()，把上一代日志物理抹掉。

Q9. 能把数据恢复到昨天吗？

热副本不行（它只有当前一份，误删会跟着复制）。要日切有两条路： 每夜停副本 → treedb-dump 一份 → 重新起副本（或不停服的 treedb-backup --primary）；或者定期停服冷备份。 要「恢复到昨天 14:03」这种中间点粒度，就得让服务端从第一天带 --archive-dir，之后 treedb-pitr --to-seq N（N 取 --stats 打出的 seq 行）——v0.6.0 起有，见 §6.11。

Q10. 通用表有性能数据吗？

未实测。benches/ 下没有 RowPut/RowList 的基准， treedb-micro 也只测 lookup / readdir / create / unlink。 通用表目前只有复杂度声明：RowGet O(1)、RowCount 主键 O(1) / 索引列 O(命中数)、 RowList 前缀范围扫描 O(limit + log n)。引用时请标注「复杂度推算，未实测」。
